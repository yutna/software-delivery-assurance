# การนำร่อง B — ภาครัฐ (synthetic)

**สถานะ:** การนำร่องภายใน เสร็จเมื่อ 2026-10-28
**ไลบรารี:** SRAS 0.8.0 ที่ commit `2264312`
**ภาคธุรกิจ:** ภาครัฐ, overlay `TH-PUB`
**ข้อมูล:** synthetic เท่านั้น ไม่มีชื่อหน่วยงาน หลักฐานจริง หรือรายละเอียดจากระบบจริง

## วัตถุประสงค์

ทดสอบว่าทีมส่งมอบงานภาครัฐเลือก Core พร้อม overlay ภาครัฐ หาได้ว่าข้อกำหนดและ
gate ใดใช้บังคับ ประเมินบริการ และรัน checks ได้หรือไม่ การนำร่องยังเปรียบเทียบผลกับ
`examples/public-sector-synthetic/`

## ขอบเขต

- SRAS Core, profile `full`, tier 2
- Modules `SRAS-INT`, `SRAS-RGD`, `SRAS-CLD`
- Overlay `TH-PUB`
- instance ใหม่จาก `sras init` และตัวอย่าง synthetic ภาครัฐ

นอกขอบเขต: หน่วยงานจริง บริการจริง ข้อมูลส่วนบุคคล การทบทวนทางกฎหมาย ผู้ตรวจทาน
ภายนอก และพฤติกรรมการจัดซื้อจัดจ้างในกระบวนการจริง

## วิธีการ

การนำร่องใช้ขั้นตอนเดียวกับ pilot A เพื่อให้เปรียบเทียบกันได้

1. สร้าง instance แบบ full profile และตั้ง selection เป็น module ทั้งสามและ `TH-PUB`
2. อ่านข้อกำหนด `TH-PUB` ทุกข้อและ evidence ที่คาดหวัง
3. คำนวณชุดข้อกำหนดที่ resolve ได้สำหรับ tier 2 และเปรียบเทียบกับชุดที่ประเมินใน
   ตัวอย่าง
4. ตรวจ gate ที่ประเมินแล้วเทียบกับประเภท evidence ที่ข้อกำหนดคาดหวัง
5. รัน checks ของไลบรารี

## ผลลัพธ์

### สิ่งที่ทำงานได้

- overlay เป็น delta จริง: 12 ข้อกำหนด เป็น gate 7 ข้อ พร้อม evidence ที่คาดหวัง
  แนวทางประเมิน และแหล่งอ้างอิงของแต่ละข้อ
- หน้ากาศรัฐระบุทะเบียนเดียวกับที่ overlay อ้างอิง (`TH-CCA-001`, `TH-CYBER-001`,
  `TH-DGA-001`, `TH-PDPA-001`, `TH-PROC-001`) พร้อม WCAG 2.2 pilot A พบว่าหน้า
  การเงินไม่ตรงกับ overlay แต่หน้านี้ตรง
- การโฮสต์และถิ่นที่อยู่ของข้อมูล (`TH-PUB-006`) ครอบคลุมการเข้าถึงหรือโอนข้าม
  พรมแดน ไม่ใช่แค่สถานที่จัดเก็บ
- ตัวอย่างใช้ถ้อยคำกลาง ๆ ไม่มีชื่อหน่วยงาน ผู้ขาย หรือข้อมูลประชาชน
- checks ของไลบรารีผ่านบน repository ตัวอย่าง

### Findings

- **PS-01 — High.** ตัวอย่างภาครัฐไม่ใช่ project instance ที่ถูกต้อง: ไม่มี `assurance.yaml` และ `risk-register.yaml` และ lockfile ใช้รูปแบบเก่าที่ parser ของ project-lock ปฏิเสธ. Disposition: แก้ใน #59
- **PS-02 — High.** ตัวอย่างรายงานว่าประเมิน 7 ข้อกำหนดและ 6 gates โดยไม่มีตัวหาร แต่ selection ที่ประกาศ resolve ได้ 112 ข้อกำหนดและ 47 gates จึงมี 41 gates ที่ยังไม่ถูกประเมิน. Disposition: แก้ใน #59
- **PS-03 — Medium.** `TH-PUB-003` เป็น gate ที่ไม่มีเป้าหมาย accessibility ขั้นต่ำ และ schema ของโปรเจกต์ไม่มีฟิลด์บันทึกเป้าหมายที่ตกลง. Disposition: คำถามกฎหมาย #131
- **PS-04 — High.** schema ของโปรเจกต์ไม่มีฟิลด์สำหรับหน่วยงานผู้ว่าจ้างหรือเลขที่สัญญา จึงเชื่อม `TH-PUB-001` กับหน่วยงานที่ให้สัญญาไม่ได้. Disposition: เลื่อนไป #132
- **PS-05 — Medium.** `TH-PUB-005` กำหนดให้ open data มี licence แต่ไม่ได้ระบุชุด licence ที่ยอมรับ ข้อความใดก็ผ่าน. Disposition: คำถามกฎหมาย #130
- **PS-06 — Low.** `TH-PUB-003` อ้าง WCAG 2.2 ซึ่งไม่มีรายการในทะเบียน จึงไม่มีการติดตามเวอร์ชันและวันทบทวนร่วมกับแหล่งอื่น. Disposition: เลื่อนไป #135
- **PS-07 — Medium.** ไม่มีการตรวจประเภท evidence ว่าเพียงพอ `TH-PUB-001` คาดหวัง document, contract และรายงานผลผู้ขาย แต่ตัวอย่างทำ gate เป็น `verified` ด้วย document เดียว. Disposition: เลื่อนไป #134

## รายละเอียดของ findings ระดับ high

### PS-01 — ตัวอย่างไม่ใช่ instance ที่ถูกต้อง

ไดเรกทอรีมี `assessment.yaml`, `evidence-index.yaml`, `claims.yaml`,
`assurance.lock.yaml` และ `evidence/` แต่ไม่มี `assurance.yaml` และ
`risk-register.yaml` lockfile ไม่ตรงกับ schema ของ project-lock ปัจจุบัน: ไม่มี
`lockfile_version` และ `inputs`, `sras.checksum` เป็น `null` และไฟล์มีฟิลด์
`generated_at` และ `notes` ที่ schema ไม่อนุญาต

นี่เป็นสาเหตุเดียวกันกับ finding PF-01 ของ pilot A ตัวอย่างสี่ในห้าแห่งมีปัญหา
เดียวกัน มีเพียง `examples/e2e-project/` ที่เป็น instance สมบูรณ์ CI ตรวจเนื้อหา
ตัวอย่างแต่ไม่เคย parse ตัวอย่างภาคธุรกิจทั้งสี่เป็น project instance

### PS-02 — slice ที่ประเมินไม่ได้ระบุตัวหาร

ที่ tier 2 selection ที่ประกาศ resolve ได้ 112 ข้อกำหนด เป็น gate 47 ข้อ
ตัวอย่างประเมิน 7 ข้อกำหนด เป็น gate 4 ข้อ และครอบ 4 จาก 12 ข้อกำหนด `TH-PUB`
README ระบุว่า "7 assessed requirements, including 6 gates" โดยไม่บอกว่ามีกี่
gate ที่ใช้บังคับ

overlay เองมี gate 7 ข้อ ผู้อ่านที่เห็น "6 gates" และไม่รู้ตัวหารอาจเข้าใจว่า
ตัวอย่างเป็นการประเมิน gate ครบถ้วน มี gate 41 ข้อที่ไม่ถูกประเมินและไม่ถูกระบุ

### PS-04 — ไม่มีการบันทึกหน่วยงานผู้ว่าจ้าง

`TH-PUB-001` กำหนดหลักฐานการจัดซื้อจัดจ้าง สัญญา การส่งมอบ ใบสั่งเปลี่ยนแปลง และ
ผลการดำเนินงานของผู้ขายสำหรับแต่ละบริการ project instance บันทึกชื่อโปรเจกต์และ
owner แต่ไม่บันทึกหน่วยงานที่ให้สัญญา เลขที่สัญญา หรือวิธีจัดซื้อจัดจ้าง ผู้อ่านจึง
ไม่รู้ว่ากฎของหน่วยงานใดใช้บังคับ และผู้ประเมินเชื่อมหลักฐานกับหน่วยงานผู้ว่าจ้าง
ไม่ได้

ตัวอย่างผ่าน gate ด้วยเอกสารทั่วไปหนึ่งฉบับ ช่องว่างนี้จึงมองไม่เห็นในชุดทดสอบ
ปัจจุบัน

## ข้อจำกัด

- ผู้ประเมินหนึ่งคน บริการ synthetic หนึ่งบริการ ไลบรารีหนึ่งเวอร์ชัน
- ไม่ได้ทดสอบบันทึกการจัดซื้อจัดจ้าง สัญญา หรือกระบวนการของหน่วยงานจริง
- ไม่ได้ทดสอบ lite profile หรือบริการข้ามหน่วยงาน
- ไม่มีผู้ตรวจทานภายนอกหรือผู้ตรวจทานกฎหมายที่มีคุณสมบัติเข้าร่วม
- จำนวนที่ resolve ได้ขึ้นกับ tier และ selection; selection อื่นให้ตัวหารอื่น

## คำถามที่ยังเปิดอยู่

คำถามเหล่านี้เป็นคำถามทางกฎหมาย repository บันทึกไว้และไม่ตอบเอง

- WCAG เวอร์ชันและระดับ conformance ใดใช้กับบริการภาครัฐไทย และคำตอบแตกต่างตาม
  ประเภทหน่วยงานหรือไม่ ดู #131
- ข้อกำหนด licence ใดที่ยอมรับได้สำหรับข้อมูลเปิดภาครัฐ ดู #130
